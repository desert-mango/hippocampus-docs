# Contributing to the HippoCampus docs

Welcome! This site is edited by the lab, for the lab — and **you do not need to code,
install anything, or know git** to fix it. If you can edit a text box in a browser,
you can fix this site.

## The five-minute fix (all in your browser)

1. Find the file to change (table below).
2. Open it on GitHub and click the **pencil icon** (top right of the file view).
3. GitHub says it will **fork** the repository for you — accept. (A fork is your own
   copy; you cannot break anything.)
4. Make your edit. Click the **Preview** tab to see it rendered.
5. Click **Commit changes…** → **Propose changes** → **Create pull request**.

That's it. A pull request (PR) is a suggestion; nothing goes live until it is
reviewed and merged.

## What happens after you click

- **First PR only:** the automatic check waits for Kyle to press **"Approve and
  run"**. Kyle has to press a button before the robot check runs — this is normal,
  it is not you.
- The check runs `tools/check.py` on your change. A green ✓ means the site's rules
  pass. A red ✗ shows the exact problem in the check's summary — fix it with the
  same pencil editor on the same branch, and the check runs again.
- **The only check that is yours is `check`.** Anything mentioning `search/` (the
  `search-shard-advisory` job) is a note for the maintainer — no action for you.
- A human will respond within about **48 hours**. When Kyle merges, the site
  deploys automatically.

## Which file do I edit?

| To change… | Edit… |
|---|---|
| Words on a setup page | `content/setup/<group>/<page>.md` |
| A project's facts (name, status, repos) | `data/projects.json` |
| A project's story | `content/projects/<id>.md` |
| An agent-tool page | `data/tools.json` + `content/tools/<id>.md` |
| The People roster (About page cards) | `data/people.json` |
| The About page prose | `content/about.md` |
| The home page cards | `data/site.json` |

Adding a **brand-new setup page** or restructuring sections is different — see
"Bigger changes" below.

## The two JSON rules that actually bite

Files under `data/` are strict JSON. Only two rules trip people up:
**double quotes only**, and **no comma after the last item**.

```jsonc
// WRONG — single quotes, and a trailing comma:
{ 'name': 'uuv02', "status": "active", }

// RIGHT:
{ "name": "uuv02", "status": "active" }
```

If you get it wrong, the check tells you where, e.g.
`data/projects.json:41:7: … (strict JSON — no trailing commas, double quotes)` —
line 41, column 7. A missing field looks like:
`data/tools.json: tools[3] (id 'foo') missing required key "tagline"`.

## Copy-paste templates

**A repository entry** (inside a project's `"repos"` list in `data/projects.json`):

```json
{ "name": "<org-repo-name>", "role": "<what it does in this project>",
  "url": "https://github.com/HippoCampusRobotics/<org-repo-name>" }
```

**A person** (inside a group's `"people"` list in `data/people.json` — set `photo`
and `link` to `null` unless you have real values; a photo must first be uploaded by
the maintainer, so ask via an issue or leave it `null`):

```json
{ "name": "Ada Example", "title": "Master Student", "photo": null, "link": null }
```

**A note box** (in any content page — types: `adm-note`, `adm-attention`,
`adm-warning`, `adm-todo`):

```html
<div class="adm adm-note"><p class="adm-title">Note</p>

Your note text here (Markdown works inside).

</div>
```

**Tabs** (keep the blank lines exactly as shown):

```html
<div class="tabs">

<div class="tab" data-label="Option A">

Content for A.

</div>

<div class="tab" data-label="Option B">

Content for B.

</div>

</div>
```

## Common fixes, worked

- **A wrong pin number on a setup page** (the classic first fix): edit
  `content/setup/raspberry-pi/pinout.md` with the pencil, fix the number, propose.
- **A tool's description is stale**: in `data/tools.json`, find the tool's entry and
  edit its `"tagline"` value. Mind the two JSON rules.
- **Adding a whole project** (the heaviest case, two files in ONE PR): add an entry
  to `data/projects.json` (`id`, `name`, `status`, `tagline`, `file`, `repos`) AND
  create `content/projects/<id>.md` with the story. **Between the two commits your
  PR's check will be red — that is expected.** Commit both files to the same PR,
  then ask for review.
- **Updating the People roster**: edit `data/people.json` using the person template
  above; new photos are a maintainer step (open an issue for that part).

## Bigger changes: open an issue instead

`data/setup.json` (the setup page list and order) is **generated by a converter**
that rewrites it wholesale — a hand-added page would be silently destroyed on the
converter's next run. So: adding a new setup page, or restructuring sections, is an
**issue, not a PR** (there is a "Content fix" issue template — page link + what is
wrong + suggested wording). Editing the *words* of existing setup pages is always
fair game. The issue route is also perfect if you'd rather report a mistake than
edit anything — that counts as contributing too.

## Please don't touch

`js/`, `css/`, `tools/`, `search/`, `index.html`, `.github/` — the site's machinery
(including the vendored `js/marked.min.js`). PRs touching these need a code review,
not a content review; if you believe one needs a change, say why in the PR text or
open an issue.

## For the technically inclined (optional)

Clone the repo and run `./tools/serve.sh` → http://localhost:8130 for a live local
preview (plain `file://` cannot fetch content). Run the same gate CI runs with
`python3 tools/check.py` — it must print `check.py: all green`. There is nothing to
install and nothing to build: what you edit is what serves.
