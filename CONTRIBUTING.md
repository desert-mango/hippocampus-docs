# Contributing to the HippoCampus docs

Welcome! This site is edited by the lab, for the lab — and **you do not need to code,
install anything, or know git** to fix it. If you can edit a text box in a browser,
you can fix this site.

## The five-minute fix (all in your browser)

1. Find the file to change (table below).
2. Open it on GitHub and click the **pencil icon** (top right of the file view).
3. **Lab members** (you have Write access): your change goes on a new branch in this
   repository. **Everyone else:** GitHub says it will **fork** the repository for you —
   accept. (A fork is your own copy; you cannot break anything.)
4. Make your edit. Click the **Preview** tab to check the text.
5. Click **Commit changes…** → (lab members: **Create a new branch for this commit and start
   a pull request**) → **Propose changes** → **Create pull request**.
6. Lab members can then click **Sign in to edit** at the bottom of any page of the site and
   open the Editor's **Proposals** tab. There you see your change on its page (**Show on
   page**). Nathalie or a Maintainer approves and merges it.

**Or use the site editor (lab members):** open the page on the site, click **Sign in to
edit** at the bottom, and sign in with GitHub. Editor mode turns on. Click the part of the
page you want to change and type right there; your changes show as suggestions. Click an image
to replace it, or drag it to move it. **Send for review** in the bubble at the top right makes
the proposal. The steps are in section 1b of
[`docs/maintainer-protocols.md`](docs/maintainer-protocols.md).

That's it. A pull request (PR) is a suggestion; nothing goes live until it is
reviewed and merged. The step-by-step protocols for reviewers are in
[`docs/maintainer-protocols.md`](docs/maintainer-protocols.md).

## What happens after you click

- **From a fork, first PR only:** the automatic check waits for a maintainer to press
  **"Approve and run"** — this is normal, it is not you. Lab members working on a
  branch in this repository never wait for it.
- The check (`check`) runs `tools/check.py` on your change. A green ✓ means the site's
  rules pass. A red ✗ lists the exact problem under "What to fix (file, line, message):" in
  the Editor's Proposals tab (and in full in the check's summary) — fix it with the same
  pencil editor on the same branch, and the check runs again.
- Nathalie or a Maintainer she names looks at the change on its page in the Proposals tab,
  approves, and merges. The site then deploys automatically.
- **The robot's commit:** right after a merge, the site's robot (`hippocampus-derive[bot]`) adds a commit named
  `derive: regenerate derived data after <short sha>`. It rebuilds the search index and
  graph data from your change — no action for you. After a merge that adds a page, the
  old site keeps showing for one to three minutes, until that commit deploys.
- **Undoing a merged change:** open the merged PR on GitHub (the Proposals tab's
  **Undo on GitHub** button takes you there), click GitHub's **Revert** button, and the
  new PR it opens goes through review like any other.

## The two JSON rules that actually bite

Files under `data/` are strict JSON. Only two rules trip people up:
**double quotes only**, and **no comma after the last item**.

```jsonc
// WRONG — single quotes, and a trailing comma:
{ 'name': 'uuv02', "status": "active", }

// RIGHT:
{ "name": "uuv02", "status": "active" }
```

If you get it wrong, the check tells you where, e.g.
`data/projects.json:41:7: … (strict JSON — no trailing commas, double quotes)` —
line 41, column 7. A missing field looks like:
`data/tools.json: tools[3] (id 'foo') missing required key "tagline"`.

## Copy-paste templates

**A repository entry** (inside the `"repos"` list of that project's own file, `data/projects/<id>.json`):

```json
{ "name": "<org-repo-name>", "role": "<what it does in this project>",
  "url": "https://github.com/HippoCampusRobotics/<org-repo-name>" }
```

**A person** (inside a group's `"people"` list in `data/people.json` — set `photo`
and `link` to `null` unless you have real values; a photo must be a site image: in the
site editor, New person's **Photo from Media** picks or uploads one; otherwise leave it
`null`):

```json
{ "name": "Ada Example", "title": "Master Student", "photo": null, "link": null }
```

**A note box** (in any content page — types: `adm-note`, `adm-attention`,
`adm-warning`, `adm-todo`):

```html
<div class="adm adm-note"><p class="adm-title">Note</p>

Your note text here (Markdown works inside).

</div>
```

**Tabs** (keep the blank lines exactly as shown):

```html
<div class="tabs">

<div class="tab" data-label="Option A">

Content for A.

</div>

<div class="tab" data-label="Option B">

Content for B.

</div>

</div>
```

## Common fixes, worked

- **A wrong pin number on a setup page** (the classic first fix): edit
  `content/setup/raspberry-pi/pinout.md` with the pencil, fix the number, propose.
- **A tool's description is stale**: in `data/tools.json`, find the tool's entry and
  edit its `"tagline"` value. Mind the two JSON rules.
- **Adding a whole project** (the heaviest case, three files in ONE PR): add
  `{"id": "<id>", "add": [], "remove": []}` to the list in `data/projects.json`, create
  `data/projects/<id>.json` with its facts (`name`, `status`, `tagline`, `file`, `repos`) AND
  create `content/projects/<id>.md` with the story. **Between the commits your PR's check will
  be red — that is expected.** Commit all three to the same PR; a site admin approves a new
  project. After that, the people with commits in the project's repositories (plus anyone an
  admin adds) look after the project's two files.
- **Updating the People roster**: on the Team page, turn Editor on: drag a card, or click it
  for Move up / Move down / Move to Alumni / Pin; the "+" card adds a person. Or edit
  `data/people.json` using the person template above (`pinned: true` keeps someone in the group
  they are in: on the current team without recent GitHub work, or in the alumni despite it). New
  photos are a Desert Mango step (open an issue for that part).
- **Renaming or removing an existing id** (a project, a tool, a setup page, a people
  group) is a Desert Mango change: hand-made graph links point at those ids, and the
  check refuses the change with a line ending `renaming or removing an existing id needs
  Desert Mango (docs/maintainer-protocols.md)`. Open an issue instead.

## Bigger changes: open an issue instead

`data/setup.json` (the setup page list and order) is **generated by a converter**
that rewrites it wholesale — a hand-added page would be silently destroyed on the
converter's next run. So: adding a new setup page, or restructuring sections, is an
**issue, not a PR** (there is a "Content fix" issue template — page link + what is
wrong + suggested wording). Editing the *words* of existing setup pages is always
fair game. The issue route is also perfect if you'd rather report a mistake than
edit anything — that counts as contributing too.

## Please don't touch

`js/`, `css/`, `tools/`, `api/`, `cms/`, `search/`, `data/graph/`, `index.html`,
`vercel.json`, `.github/` — the site's machinery (including the vendored
`js/marked.min.js`) and its data. **Never commit the derived files under `search/` or
`data/graph/`** (the "Derived outputs" row above): the robot rebuilds them after every
merge. The authored graph overlays there (the "Authored graph overlays" row) are committed
only as a Desert Mango change. PRs touching machinery get a **machinery** badge in the
Proposals tab and need a code review by Desert Mango, not a content review; if you believe
one needs a change, say why in the PR text or open an issue.

## For the technically inclined (optional)

Clone the repo and run `./tools/serve.sh` → http://localhost:8130 for a live local
preview (plain `file://` cannot fetch content). Run the same gate CI runs with
`python3 tools/check.py` — it must print `check.py: all green`. There is nothing to
install and nothing to build: the deploy runs that same gate and then serves the
repository as-is. `node tools/dev_site.mjs` (port 8131) also runs the `api/` functions for
local site-editor testing.
