# hippocampus-docs

The documentation home of the **HippoCampusRobotics** lab: setup guides (migrated page
for page from the old Sphinx site), the team's projects (every org repository, grouped
and explained), in-browser search over code and CAD (phase 2), and the lab's agent tools.

**Static site, no framework, no npm.** There is no build step that produces files: the
deploy runs the gate, `python3 tools/check.py`, as its build command (`vercel.json`
`buildCommand`) and serves the repository as-is, so a red gate never goes live. The one
vendored library is `js/marked.min.js` (marked v12.0.2, MIT, sha256 pinned in
`tools/check.py`).

## Run it

```sh
./tools/serve.sh          # static preview on http://localhost:8130
node tools/dev_site.mjs   # function-aware preview on http://localhost:8131 (also runs api/*.js)
```

`dev_site.mjs` is the one to use for local CMS testing: it serves `/cms/` and every
`api/*.js` function, and loads `.env.local` at the repo root (gitignored; `--dotenv PATH` for
another file) with the keys `GH_APP_CLIENT_ID`, `GH_APP_CLIENT_SECRET` and
`OPENROUTER_API_KEY` (placeholders like `<yours>`; the real values live in the Vercel
project's environment variables).

Vercel serves the committed files byte-identical after the gate passes; nothing is generated
at deploy time.

## Edit it

| To change… | Edit… |
|---|---|
| Words on a setup page | `content/setup/<group>/<page>.md` |
| The setup page list and order | `data/setup.json`, generated by `tools/rst_convert.py`: re-run the converter, never hand-edit; a lab member asks for a new page with an issue |
| A project's facts (name, status, repos) | `data/projects.json` |
| A project's story | `content/projects/<id>.md` |
| An agent-tool page | `data/tools.json` + `content/tools/<id>.md` |
| The People roster (About page cards) | `data/people.json` |
| The About page prose | `content/about.md` |
| The home page cards | `data/site.json` |
| An image | Hosted on Cloudinary (folder `hippocampus-docs/`) and mapped in `data/cloudinary-manifest.json`; pages reference the manifest URL. Lab members upload in the site editor's Media tab (`/cms/#/media`), which adds the manifest entry |
| Derived outputs: `search/site.json`, `search/manifest.json`, `data/graph/wiki.json`, `data/graph/contributors.json`, the `"source": "derived"` entries of `summaries.json` and the `terms` of `xref-terms.json` | Nothing by hand: regenerated by `tools/derive.py`; never committed in a pull request; `derive.yml` commits them on `main` |
| Authored graph overlays: `data/graph/edges-authored.json`, the `"source": "authored"` entries of `summaries.json`, the `rejected` and `stoplist` lists of `xref-terms.json` | Hand-kept inputs the builders preserve. The edges and the authored summaries key on registry ids, and the builders fail by name when an id they point at disappears, so renaming or removing an existing id is a Desert Mango change; the `rejected` and `stoplist` lists are word lists a rename cannot break |
| The site editor: `cms/`, `js/cms*.js`, `js/source.js`, `js/sanitize.js`, `api/auth.js`, `api/media.js` | Code, not content (a code review by Desert Mango); the protocols are `docs/maintainer-protocols.md` |

Then run the gate — it must pass before every commit:

```sh
python3 tools/check.py
```

It validates strict-JSON registries, file existence both ways (no orphans), internal
links, image references (including the Cloudinary manifest — see below), the setup parity
counts, and the projects-coverage rule (every org repo in exactly one project). Never
weaken a check to get to green — fix the content.

Derived data (`search/site.json`, `search/manifest.json`, `data/graph/wiki.json`,
`data/graph/contributors.json` and the derived parts of `summaries.json` and
`xref-terms.json`) is regenerated by `python3 tools/derive.py`.

## CI

Two workflows. `.github/workflows/check.yml` (job `check`) runs `python3 tools/check.py`
verbatim on every pull request and every push to `main`; on pull requests it first
regenerates the derived data in the workspace (not committed), and after a red gate it
re-emits each finding as a GitHub annotation. `.github/workflows/derive.yml` (job `derive`)
runs after every push to `main`: it regenerates the derived data, runs the gate, and commits
the result as `github-actions[bot]`.

When images, the Cloudinary manifest, or people-card links changed, also run the network
half of the gate — it probes exactly those URLs for liveness (check.py itself stays
offline; ordinary external links in page prose are not probed):

```sh
python3 tools/check_urls.py
```

## Images: Cloudinary

Site images are served from Cloudinary (folder `hippocampus-docs/`), mapped in
`data/cloudinary-manifest.json` (source file → public_id → URL, with the source's
sha256). Local originals stay in `assets/` as upload sources — they are not orphans, and
editing one without re-uploading trips the manifest digest check. To add an image: upload
it with the cloudinary-upload skill (credentials live in the portfolio repo), add a
manifest entry, and reference the manifest URL from the page. Still local by design:
`assets/hippo.svg` (brand mark) and the `.stl`/`.3mf`/`.pdf` download files.

## Where things come from

- `tools/rst_convert.py` performed the one-shot RST→Markdown migration from a clone of
  `HippoCampusRobotics/docs`; the page-for-page account (71 migrated, 26 dropped with
  reasons) is `docs/setup-parity.md`. Re-running the converter regenerates
  `content/setup/`, `assets/setup/`, `data/setup.json`, and the parity table.
- `data/org-repos.json` is the org snapshot the projects coverage is checked against;
  `data/cad-tree.json` is the canonical CAD repo's file list (search input, phase 2).
- `docs/site-plan.md` is the architecture record; `PROGRESS.md` the phase log.

## Status

**Live: <https://hippocampus-docs.vercel.app>**. Search runs on the committed precomputed
index (`search/`, 75 shards, 0.42 MB; 10/10 keyword probes at rank 1 —
`data/search-probes.json`). Multi-word queries can also be answered by the librarian
(`api/librarian.js`), which walks the site's own knowledge graph and degrades to keyword
results when it is unreachable.

**Site editor:** `/cms/` is the lab's editing and review tool: sign in with GitHub, edit a
page with a live preview and propose it (**Edit**), upload images (**Media**), then see each
pull request's gate result and a rendered preview, approve and merge (**Review**). The
github.com pencil still works as a second way. The protocols for the lab are
`docs/maintainer-protocols.md`; the plan is `docs/cms-v2-plan.md`.
