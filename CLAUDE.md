# hippocampus-docs — agent operating rules

Static site. There is no build step that produces files: the deploy runs
`python3 tools/check.py` as its build command (`vercel.json` `buildCommand`) and serves the
repository as-is; a red gate never goes live.

## The one law

Run `python3 tools/check.py` after every change; it must print "all green" before any
commit. When images, `data/cloudinary-manifest.json`, or people-card links changed, ALSO
run `python3 tools/check_urls.py` (the network half of the gate — it probes exactly those
URLs; check.py stays offline) and it must pass. Never weaken a check to pass it — fix the
content it complains about. The same gate is the deploy's build command (`vercel.json`
`buildCommand`): there is no build step that produces files, the repository is served as-is,
and a red gate never goes live.

Notes on the rows (agents):

- Setup prose is Markdown; the raw-HTML wrappers `<div class="adm adm-note">` /
  `<div class="tabs">` are part of the dialect. Script-capable markup is refused by the gate.
- Setup structure: the converter also regenerates `docs/setup-parity.md`. It reads
  `data/cloudinary-manifest.json`: images with a manifest entry are emitted as Cloudinary URLs
  (the site serves images from the CDN; local `assets/` files are the upload sources); an image
  without an entry is listed loudly at the end of the run and must be uploaded before commit.
- Images: upload via the cloudinary-upload skill from the portfolio repo (credentials live
  there), add the manifest entry, reference the manifest URL. Local originals stay in `assets/`
  as sources. Manifest entries with `"source": null` are CMS uploads: they have no local file,
  and their sha256 is of the uploaded bytes. Exceptions that stay local: `assets/hippo.svg`
  (brand mark) and the `.stl`/`.3mf`/`.pdf` downloads.
- Projects: `data/projects.json` is strict JSON. Coverage rule: every org repo in exactly one
  project.
- People roster: a card is name, title, optional photo (a manifest URL), optional link; link
  decisions are recorded in `docs/people-links.md`. Cards without a link get no hover affordance.
- Home/About: `data/site.json` holds the home cards, kicker and lead; the People roster mounts
  inside `content/about.md`.
- Derived outputs: after content changes run `python3 tools/derive.py` (plain python3; it runs
  `build_wiki_graph.py` and `build_search_index.py --site-only`, and `build_contributors.py`
  with `--contributors`). In a pull request, do not commit its output: CI regenerates it in the
  workspace and `derive.yml` commits it after the merge. When pushing `main` directly, commit it
  with the change so the gate (and that push's deploy) is green on its own. The full code
  reindex needs clones + graphify (see the `build_search_index.py` header).

## Contribution pipeline

- CI runs `python3 tools/check.py` VERBATIM on every pull request and every push to
  `main` (`.github/workflows/check.yml`, job `check`) — never a copy, never a weakened
  variant. Around that one command: on pull requests only, a step first runs
  `python3 tools/derive.py` to regenerate the derived outputs in the workspace (not
  committed), so the gate judges what `main` will hold after the merge; on push to `main`
  nothing is regenerated and the gate judges the committed tree, as the deploy build does.
  After a red gate, a step re-emits each finding as a GitHub annotation
  (`tools/derive.py --annotate`); the CMS Review tab reads those. The old
  `search-shard-advisory` job is retired.
- The second workflow, `.github/workflows/derive.yml` (job `derive`), runs after every push
  to `main`: it regenerates the derived outputs, runs the gate, and commits them as
  `github-actions[bot]` (`derive: regenerate derived data after <short sha>`); it pushes
  nothing when the gate is red.
- Who does what: lab members are Write collaborators who work on branches in this
  repository (no fork, no "Approve and run"); Nathalie (Admin) and the Maintainers she names
  review and merge; outsiders use forks. The site editor (`/cms/`) only ever opens pull
  requests, one commit per proposal. The day-to-day steps for the lab are
  `docs/maintainer-protocols.md`.
- `.github/` is part of the law, not contraband to tidy away: deleting or renaming a
  workflow or its `check` job silently removes the gate from pull requests, and the CMS
  Review tab reads the check run by that name. Treat any `.github/`, `tools/`, `api/`, `js/`,
  `cms/` or `vercel.json` diff as code review, not content review — a PR-head workflow can
  redefine the gate that judges it.
- The ONE piece of third-party code CI runs is the SHA-pinned `actions/checkout` step. The
  one network data input is `derive.yml`'s read of public contributor counts from the GitHub
  API (`gh api`, through `build_contributors.py`, only when `data/projects.json`,
  `data/org-repos.json` or `data/people.json` changed); its output is committed to
  `data/graph/contributors.json` and judged by the gate like any other file. Nothing new
  enters the serving path or any contributor's local path; the deployed bytes stay
  byte-identical to the repo.
- Every new `.js`, `.mjs` or `.py` file carries the five-line attribution header (`Author`,
  `Project`, `Last substantive modification`, `Affiliation`, `Purpose`) and an `included`
  entry with its baseline sha256 in `tools/attribution_headers.json`;
  `tools/check_attribution_headers.py` runs inside the gate and fails on a missing header or
  entry.
- The edit map above is CANONICAL. `CONTRIBUTING.md` and `README.md` carry its table rows
  verbatim; when the map changes, reconcile those copies to this one — never the other way
  around.
- `tools/check.py` carries a required-keys dict (reader-inputs pass,
  `READER_REQUIRED_KEYS`). The rule has four parts: a new bare key dereference in
  any file that reads a `data/*.json` registry (today: `api/media.js` (manifest only),
  `js/app.js`, `js/cms-core.js`, `js/cms.js`, `js/graph.js`, `tools/bench_librarian.mjs`,
  `tools/build_contributors.py`,
  `tools/build_repo_graphs.py`, `tools/build_search_index.py`, `tools/build_wiki_graph.py`,
  `tools/check.py`, `tools/check_urls.py`, `tools/derive.py` (paths only), `tools/rst_convert.py`
  — re-derive the list with
  `grep -rln "data/[a-z_-]*\.json" . --exclude-dir=.git --exclude-dir=data --exclude-dir=search`;
  `api/media.js` reads only `data/cloudinary-manifest.json`, which has its own gate section;
  `tools/derive.py` only passes registry paths to `git diff` and dereferences no key; the grep
  also matches Markdown files and `tools/tests/`, which are not readers; `js/source.js` does not
  match, because it fetches registry files on the readers' behalf and dereferences no key)
  gains a `keys` entry; a new list a reader ITERATES gains a `lists` entry (or an `each` entry
  when its items are objects) — this is the part that fails silently when forgotten,
  because a string in a list's place is an iterable of characters, not a type error;
  a nested object a reader dereferences into gains an `objects` entry (its child spec
  covers the inner keys); and a value gets a `types`/`str_lists` entry ONLY when a reader crashes on the
  wrong type or is silently wrong about it (the string `"false"` is truthy) — never
  as a general string-ness check on titles and names. A new `data/*.json` registry
  gets its own block (registries with their own dedicated section — the Cloudinary
  manifest, the People roster, everything under `data/graph/` — are listed as
  exclusions in its comment).

## Hard rules

- No credentials, key material, or personal emails in content — check.py enforces;
  placeholders look like `<yours>`.
- No new dependencies, no npm, no build tooling. Vendored marked stays sha256-pinned.
- No third-party script from any CDN — not the Cloudinary widget, not a CMS bundle. A
  browser library is vendored as one file and sha256-pinned.
- Preview: `./tools/serve.sh` → http://localhost:8130 (file:// cannot fetch content).
  `node tools/dev_site.mjs` → http://localhost:8131 is the function-aware sibling: it also
  runs every `api/*.js` and loads `.env.local` (`--dotenv PATH` for another file).
- Credentials live in the Vercel project's environment variables and nowhere else in the
  deploy; a local copy for `dev_site.mjs` goes in `.env.local`, which is gitignored:

  | Variable | Lives in | Used by |
  |---|---|---|
  | `GH_APP_CLIENT_ID`, `GH_APP_CLIENT_SECRET` | Vercel env (Production + Preview) | `api/auth.js` (CMS sign-in) |
  | `OPENROUTER_API_KEY` | Vercel env (Production + Preview) | `api/librarian.js` |
  | `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, `CLOUDINARY_API_SECRET` | Vercel env (Production + Preview), with the key pair made for this site | `api/media.js` (signed uploads) |
  | `GH_VIEWER_CLIENT_ID`, `GH_VIEWER_CLIENT_SECRET` | Vercel env, after the handoff | the read-only viewer App |
- **Done means merged.** Work is not done until it is safely merged into `main` and
  pushed. Kyle is the sole or primary contributor of this project (true of every project
  so far, this one included), so an agent working for Kyle integrates through the
  git-worktree ownership gate and pushes `main` itself at task completion — it does not
  wait for Kyle. Every push deploys the site (Vercel), so `python3 tools/check.py`
  must be green in the integration worktree first; that gate stays. A verified task
  branch left unmerged "waiting on Kyle" is stranded work, not done work: say "stranded,
  not done" and list the unmerged commits.
  - Two paths, by who is pushing. Outside contributors and lab members use the
    pull-request pipeline above (`.github/`, `CONTRIBUTING.md`) and never push `main`.
    Kyle's agents push `main` directly with Kyle's own identity: `main` has no branch
    protection (declined 2026-09-06, `docs/cms-plan.md` §6 — never re-propose it), so a
    direct push just works. If protection is ever added, an agent's path becomes "open the
    PR, get `check` green, merge it" — done still means merged, never "PR opened".
  - The one exception: when Kyle is a small contributor to someone else's project, an
    agent never pushes that project's `main`; it opens a pull request against it
    instead. No project has been in that mode yet, so before using it an agent must
    verify which mode applies (repository ownership and share of commit authorship,
    e.g. `git shortlog -sne origin/main`) and say what it checked.
